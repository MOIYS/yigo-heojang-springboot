# ADR-0002: Spring Boot 전환 전 k6 성능 기준선 수립

## 상태

- 상태: Accepted
- 결정 시점: 2026-10-14
- 작성 시점: 2026-11-09
- 기록 유형: 소급 작성

## 1. 배경 및 문제

**배경:**
- 백엔드는 Spring 5.3 기반 WAR로 로컬 외부 Tomcat 9에서 실행되고 있었으며, 이후 Spring Boot 실행 JAR로 전환할 계획이었습니다.
- 기존 기능이 전환 후에도 동일하게 동작하는지는 특성화 테스트와 Newman으로 검증할 수 있었지만, 응답 시간과 요청 실패율을 비교할 성능 기준선은 마련되어 있지 않았습니다.

**문제:**
- Spring Boot 전환과 이후 기능 개선을 진행하면 응답 시간과 요청 실패율이 달라질 수 있습니다. 그러나 기존 시스템의 성능 측정값이 없으면 개선 작업 전후의 성능 변화를 확인하기 어렵습니다.
- 따라서 기존 시스템의 성능을 기준으로 이후 변경에 따른 성능 변화를 비교할 수 있도록, 기준선 수립에 사용할 테스트 데이터, 부하 모델 및 반복 측정 방식을 결정해야 했습니다.
## 2. 대안 비교

| 대안                                                         | 장점                                             | 단점                                                      |
| ---------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------  |
| A. 고정 seed와 `constant-vus` 부하로 기준선 3회 측정               | 동일한 테스트 데이터와 VU 수에서 응답 시간과 실패율을 반복 비교할 수 있음    | 서버 응답이 느려지면 요청률도 감소하므로, 일정한 요청 유입 조건에서의 처리 한계는 확인하기 어려움  |  
| B. `constant-arrival-rate` 또는 `ramping-arrival-rate` 기반 측정 | 일정한 반복 시작률에서의 성능을 측정하거나 부하를 높여 처리 한계를 탐색할 수 있음 | 충분한 VU와 부하 생성 자원이 필요하며, 단일 PC에서는 자원 경합으로 측정 결과가 왜곡될 수 있음  |

## 3. 적용한 결정 및 기술적 평가

**선택:** A안 — 성능 전용 seed를 매 회차 다시 만들고, k6로 warm-up 60초, baseline 10 VU 300초, cool-down 30초를 3회 측정해 중앙값을 기준선으로 삼음.

**당시 결정 경위:**
- 성능 테스트 도구로 k6를 채택했으며, 다른 후보와의 체계적인 비교는 수행하지 않았습니다.
- 이후 전환 전후의 성능을 동일한 조건에서 비교하기 위해 고정 데이터와 constant-vus 기반 반복 측정을 적용했습니다.

**선택 이유:**
  - **측정 목적:** 최대 처리 용량을 확인하기보다 Spring Boot 전환 전후의 응답 시간과 실패율을 비교하는 것이 목적이므로, 가상 사용자 수를 고정하는 `constant-vus`를 선택했습니다.
  - **재현성:** 동일한 테스트 데이터를 사용하고 같은 조건에서 3회 반복 측정해, 데이터 차이와 일시적인 측정 변동의 영향을 줄이고자 했습니다.

**비용 및 제약:**
- 고정 VU 조건에서는 요청 유입량과 서버의 최대 처리 용량을 통제하거나 확인하기 어렵습니다.
- 서버가 충분한 여유 용량을 가진 경우, 낮은 부하에서 측정한 결과만으로 고부하 성능의 차이를 판단할 수 없습니다.
- 또한 단일 PC의 자원 경합 등으로 측정값이 달라질 수 있으며, 지연 시간 threshold가 `p(95)>=0`으로 설정되어 성능 저하를 자동으로 판정하지 못합니다.
